# 새 스테이지 만드는 법

**코딩을 해본 적이 없어도 만들 수 있게** 썼습니다.
기존 스테이지 파일 하나를 복사해서 고치는 것이 가장 빠른 길입니다.

---

## 시작하기 전에

터미널에서 이 두 줄만 알면 됩니다.

```bash
npm install     # 처음 한 번만
npm test        # 스테이지를 고칠 때마다 실행
```

`npm test` 는 채점기라고 생각하시면 됩니다.
스테이지에 실수가 있으면 **무엇이 잘못됐는지 한국어로 알려줍니다.**

---

## 전체 흐름

```
1. 겨냥할 오개념을 정한다        ← 가장 중요한 단계입니다
2. 기존 스테이지 파일을 복사한다
3. 내용을 채운다
4. 레지스트리에 두 줄 추가한다
5. npm test 로 확인한다
```

---

## 1단계 — 겨냥할 오개념 정하기

이게 스테이지의 전부입니다. 나머지는 이걸 뒷받침하는 장치일 뿐입니다.

좋은 오개념의 조건:

- 학생이 **실제로** 자주 가지고 있다
- 학생의 일상 경험으로는 반박되지 않는다 (그래서 시뮬레이션이 필요하다)
- 한 문장으로 쓸 수 있다

| 좋은 예 | 나쁜 예 |
|---|---|
| "무거운 물체가 빨리 떨어진다" | "학생들이 물리를 어려워한다" (너무 넓음) |
| "최고점에서는 힘이 0이다" | "가속도 공식을 외우지 못한다" (오개념이 아니라 암기 문제) |
| "움직이려면 힘이 계속 필요하다" | "마찰이 있다" (오개념이 아니라 사실) |

그리고 이렇게 자문해 보세요.

> **"이 오개념을 가진 학생이 화면에서 무엇을 보면 흔들릴까?"**

그 장면이 스테이지의 중심이 됩니다.
낙하 스테이지가 진공과 공기를 **나란히** 보여주는 이유가 그것입니다.
한쪽만 보여주면 학생은 자기 경험과 충돌해서 시뮬레이션을 안 믿습니다.

## 3단계 — 내용 채우기

### 기본 정보

```ts
id: 'my-stage',                    // 영문 소문자와 하이픈만. 다른 스테이지와 겹치면 안 됩니다
title: '내 스테이지',                 // 학생에게 보이는 이름
subtitle: '한 줄 설명',
domain: '역학',                     // '역학' | '파동' | '전자기'
concepts: ['등가속도 운동', '마찰'],   // 관련 개념 태그
targetMisconception: '겨냥할 오개념을 한 문장으로',
situation: '학생에게 보여줄 상황 설명. 정답을 암시하면 안 됩니다.',
```

> ⚠️ `situation` 은 **예측을 입력하기 전에** 보이는 글입니다.
> 여기에 정답을 흘리면 스테이지 전체가 무의미해집니다.

### 학생이 만질 변수 (controls)

```ts
controls: [
  {
    kind: 'slider',
    id: 'mass',              // 코드에서 이 값을 꺼낼 때 쓰는 이름
    label: '물체의 질량',       // 학생에게 보이는 이름
    unit: 'kg',              // ★ SI 단위 필수. 무차원이면 '' 로 두세요
    min: 0.5, max: 10,
    step: 0.5,
    default: 2,
    help: '한 줄 도움말 (생략 가능)',
  },
],
```

`toggle`(켜기/끄기) 과 `select`(여러 선택지) 도 쓸 수 있습니다. 기존 파일을 참고하세요.

**변수는 3~6개가 적당합니다.** 너무 많으면 학생이 무엇을 바꿔야 할지 몰라 헤맵니다.

### 초기 세계 만들기 (build)

파라미터를 받아서 물체와 지형을 배치합니다.

```ts
build: (p) => {
  const mass = num(p, 'mass', 2);       // 슬라이더 값 꺼내기 (없으면 2)

  return createWorld({
    bodies: [
      createBody({
        id: 0,
        tag: 'ball',                     // 이름표. bodyTags 순서와 맞아야 합니다
        mass,
        radius: 0.2,
        p: { x: 0, y: 10 },              // 처음 위치 [m]
        v: { x: 3, y: 0 },               // 처음 속도 [m/s]
        restitution: 0.5,                // 반발계수 (1=완전탄성, 0=완전비탄성)
      }),
    ],
    walls: [
      { tag: 'floor', a: { x: -10, y: 0 }, b: { x: 10, y: 0 },
        restitution: 0.5, friction: 0.3 },
    ],
    fields: { gravity: { x: 0, y: -9.81 } },
  });
},
```

**단위는 전부 SI 입니다.** 길이 m, 시간 s, 질량 kg, 힘 N, 전하 C.

### 측정 채널 (measure)

그래프와 미션이 읽을 값을 정합니다.

```ts
measure: {
  channels: [
    { id: 'speed',  label: '속력',  unit: 'm/s' },
    { id: 'height', label: '높이',  unit: 'm' },
  ],
  compute: (world, out) => {
    const b = world.bodies[0]!;
    out[0] = Math.hypot(b.v.x, b.v.y);   // channels[0] = speed
    out[1] = b.p.y;                      // channels[1] = height
  },
},
```

`channels` 의 순서와 `out[...]` 의 번호가 **정확히 맞아야** 합니다.

### 예측 질문

```ts
prediction: {
  kind: 'numeric',
  prompt: '공은 몇 초 뒤에 바닥에 닿을까요?',
  unit: 's',
  min: 0, max: 10, step: 0.1,
  tolerance: 0.05,                       // 5% 이내면 예측 배지
  truth: (p) => Math.sqrt(2 * num(p, 'height', 10) / 9.81),
},
```

`truth` 는 **해석해(공식)** 로 쓰는 것이 원칙입니다.
공식으로 못 쓰는 경우에만 시뮬레이션 결과를 쓰세요.

`kind: 'choice'` 로 4지선다도 만들 수 있습니다(`truth` 는 정답 번호, 0부터 셈).

### 미션 3개 (별 3개)

```ts
missions: [
  {
    id: 'reach-target',
    title: '목표 지점 도달',
    description: '학생에게 보여줄 달성 조건',
    hint: '실패했을 때 보여줄 힌트. 정답을 알려주지 말고 방향만 제시하세요.',
    check: (t, p) => traceScalarMax(t, 'speed') >= 10,
  },
  // ... 정확히 3개
],
```

`check` 는 **순수 함수**여야 합니다.
같은 입력에는 항상 같은 결과를 내야 하고, 바깥 세상(시간·난수·화면)을 읽으면 안 됩니다.

궤적을 조회하는 함수들:

| 함수 | 하는 일 |
|---|---|
| `traceScalar(t, 프레임, '채널')` | 특정 프레임의 채널 값 |
| `traceScalarMax(t, '채널')` | 실행 전체에서 최댓값 |
| `traceScalarFinal(t, '채널')` | 마지막 프레임의 값 |
| `traceAny(t, f => ...)` | 조건을 만족하는 프레임이 하나라도 있는가 |
| `traceFirstFrame(t, f => ...)` | 조건을 처음 만족하는 프레임 (없으면 −1) |
| `traceLandingTime(t, 물체번호, BF_RESTING)` | 물체가 멈춘 시각 |

**미션 3개는 이렇게 배치하는 것이 좋습니다.**

1. 그냥 실행하면 달성되는 것 (관찰 유도)
2. 변수를 하나 조절해야 달성되는 것 (탐구 유도)
3. 관계를 이해해야 달성되는 것 (개념 확인)

### 오개념 진단 문항

```ts
probe: {
  question: '실행 후 물어볼 질문',
  choices: [
    { text: '정답 선택지', correct: true,
      feedback: '왜 맞는지 설명' },
    { text: '오개념 선택지', correct: false,
      feedback: '왜 그렇지 않은지. 되감아서 보여줄 장면을 함께 안내하세요.' },
    // ... 정확히 4개, 정답은 정확히 1개
  ],
  rewindTo: (t) => traceFrameOfMax(t, 'height'),   // 오답 시 되감을 프레임
  rewindCaption: '이 순간을 보세요. ...',
},
```

> ⚠️ 오답 선택지의 `feedback` 은 **틀렸다고 혼내는 글이 아닙니다.**
> "왜 그렇게 생각했는지는 이해하지만, 화면의 이 장면을 보면 다릅니다" 라는 어조로 쓰세요.
> 예측이 빗나간 지점이 배울 게 있는 지점입니다.

`rewindTo` 는 그 오개념을 **직접 확인시킬 수 있는 결정적 순간**을 가리켜야 합니다.
말로 설명하는 대신 그 장면을 보게 하는 것이 이 앱의 방식입니다.

### 개념 정리 (explain)

마크다운으로 씁니다. 수식은 `$$...$$` 로 감쌉니다.

기존 스테이지를 보면 구조가 대체로 이렇습니다.

```
## 정리: (한 문장 결론)
(핵심 식)
### 그럼 일상에서는 왜 다르게 보일까
(오개념이 생기는 이유를 존중하며 설명)
### 한 줄 요약
```

### 마무리 설정

```ts
duration: 10,                                        // 자동 정지 시각 [s]
view: { xMin: -5, xMax: 5, yMin: -1, yMax: 12 },     // 카메라가 잡을 영역 [m]
bodyTags: ['ball'],                                  // build 의 물체 순서와 일치
```

`view` 는 파라미터에 따라 장면 크기가 달라지면 함수로 줄 수 있습니다.

```ts
view: (p) => ({ xMin: -5, xMax: 5, yMin: -1, yMax: num(p, 'height', 10) + 3 }),
```

```ts
  // ...

```

배열 순서가 곧 학생이 만나는 순서입니다.

## 5단계 — 확인하기

```bash
npm test
```

자동으로 이런 것들을 검사합니다.

- 미션이 정확히 3개인가 (별 3개 = 미션 3개)
- 진단 문항이 4지선다이고 정답이 정확히 하나인가
- 모든 슬라이더의 기본값이 min~max 범위 안에 있는가
- 그래프가 존재하지 않는 측정 채널을 참조하지 않는가
- 예측 정답이 유한한 값이고 학생이 입력할 수 있는 범위 안에 있는가
- 어떤 슬라이더를 끝까지 밀어도 카메라 영역이 뒤집히지 않는가
- 스테이지가 끝까지 돌아가고 값이 무한대나 NaN 이 되지 않는가
- 같은 조건으로 두 번 돌리면 완전히 같은 결과가 나오는가

문제가 있으면 이런 식으로 알려줍니다.

```
스테이지 정의 > 모든 스테이지가 정의 검사를 통과한다
  [{ "id": "my-stage",
     "errors": ["미션은 정확히 3개여야 합니다 (현재 2개). 별 3개 = 미션 3개."] }]
```

### 미션이 정말 달성 가능한지 확인하기

**달성 불가능한 미션은 학생 입장에서 가장 나쁜 버그입니다.**
아무리 해도 별이 안 나오면 학생은 자기 잘못이라고 생각합니다.

그래서 `tests/missions.test.ts` 의 `solutions` 목록에 **직접 달성하는 조합**을 적어두세요.

```ts
{ stage: 'my-stage', mission: 'reach-target', params: { mass: 5, speed: 12 } },
```

미션 3개를 전부 적지 않으면 테스트가 이렇게 알려줍니다.

```
해답이 없는 미션: my-stage/reach-target
```

이 목록이 있으면, 나중에 물리 모델을 고쳤을 때 **미션이 조용히 달성 불가능해지는 사고**를
자동으로 잡아냅니다. 실제로 개발 중에 이 검사가 네 건의 버그를 잡았습니다.

## 자주 겪는 문제

**Q. 물체가 트랙에서 자꾸 떨어져요**

한쪽 지지(`oneSided`) 트랙에서는 수직항력이 음수가 되면 물체가 떠납니다.
언덕 마루에서 너무 빠르면 실제로 뜨는 것이 맞는 물리입니다.
떨어지지 않게 하려면 `support: 'twoSided'` 로 바꾸세요
(레일에 물려 있는 롤러코스터가 이쪽입니다).

**Q. 마찰을 켰더니 에너지가 사라져요**

엔진은 마찰이 한 일을 자동으로 열에너지로 옮겨 적습니다.
`computeEnergy(world).total` 은 열까지 포함한 값이므로 마찰이 있어도 일정해야 합니다.
그래프에는 `total` 채널을 함께 그려서 학생이 총합을 볼 수 있게 하세요.

**Q. 그래프가 비어 있어요**

`charts` 의 `series[].channel` 이 `measure.channels[].id` 와 정확히 같은지 확인하세요.
`npm test` 가 이 실수를 잡아줍니다.

**Q. 예측 정답이 이상해요**

`truth` 안에서 파라미터를 꺼낼 때 쓴 기본값이 `controls` 의 `default` 와
다른 경우가 흔합니다. `num(p, 'speed', 20)` 의 `20` 과 슬라이더의 `default: 20` 이
같은지 확인하세요.
